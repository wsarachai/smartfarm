# web-server/

Node.js/Express hub + pre-built React/Redux dashboard served from one port.
Layout: `ls web-server/`. Dev workflow: `web-server/DEV.md`.

## Notes

- `GET /api/v1/devices` was added beyond the original two endpoints since the dashboard needs a way to fetch current state to poll.
- `GET /api/v1/health` returns `{ status, uptime, deviceCount, timestamp }` and backs the `docker-compose.yaml` healthcheck. The healthcheck probes it with `node -e` (via `http.get`) rather than `curl`/`wget`, keeping the `node:18-alpine` image dependency-free.
- **ESP32-CAM camera feed** (`src/routes/camera.js` + `src/store/frameStore.js`): the camera firmware's PUSH mode POSTs raw `image/jpeg` to `POST /api/v1/camera/frame`; the server keeps only the **latest** frame in a single-slot in-memory buffer (no SD writes) and exposes `GET /frame.jpg` (snapshot), `GET /stream` (multipart/x-mixed-replace MJPEG relay of the *pushed* frames — all viewers share the one buffer), and `GET /status`. Uses the built-in `express.raw()` — no new npm deps. Tunables: `CAMERA_MAX_FRAME_BYTES`, `CAMERA_STALE_MS`. On the camera side set `PUSH_ENABLED 1` and `PUSH_URL "http://<jetson-ip>:3000/api/v1/camera/frame"` in `include/secrets.h`.
- **Live video proxy** (`src/routes/camera.js` `GET /live` + `src/store/cameraLive.js`): the PUSH path above is ~1 frame/10s (a slideshow), and the camera's own high-fps `:81/stream` is only reachable from the camera's Wi-Fi subnet — so a browser viewing the deployed dashboard from elsewhere gets a black feed. `GET /api/v1/camera/live` fixes this: the server (on the camera's network) pulls the camera's `:81` MJPEG **once** and fans it out to all viewers **same-origin**, so any client that can load the dashboard sees live video and the camera serves a single connection (dodging its tiny concurrent-stream limit). Camera source via `CAMERA_STREAM_URL` env (default `http://192.168.0.3:81/stream`); auto-reconnects on transient drops, ends viewers on hard-down (page shows NO SIGNAL). The client's **relay** camera mode (now the default in `cameraSettings.js`) streams from `/api/v1/camera/live`; **custom** mode points the browser straight at a camera URL (needs direct reachability).
- **Server-owned dashboard settings** (`src/store/settingsStore.js` + `src/routes/settings.js`): the Settings-page **Camera Source** and **Pump Control** blocks used to live per-browser in `localStorage`; they are now **global, server-owned config** persisted to `data/settings.json` (atomic temp+rename write, on the same host volume as `camera-config.json`). `GET /api/v1/settings` returns the whole `{ cameraSource, pump }`; `POST` takes a **partial patch** (just the edited section), validates server-side (pump `url` must be http(s) since the server fetches it, `autoOffMinutes` 1–60, `sourceMode` = `relay|custom`), deep-merges, and returns the full object. Defaults are **env-seeded** (`PUMP_URL`, `PUMP_LABEL`, `PUMP_AUTO_OFF_MINUTES`, `CAMERA_SOURCE_MODE`/`_STREAM_URL`/`_SNAPSHOT_URL`, `SETTINGS_PATH`) and loaded at boot (`settingsStore.load()`). The client reads it via RTK Query (`settingsApi`, fetch-on-mount + `refetchOnFocus`/`refetchOnReconnect`, no polling; save invalidates the cache). `usePumpSettings()`/`useCameraSettings()` keep their names/shapes as thin wrappers over that query. **Camera device config (`camera-config.json`) is deliberately left separate** — it's a firmware-pulled contract, not dashboard settings.
- **Pump target is now server-owned:** the shared pump command layer (`src/store/pumpControl.js`, used by both the route and the scheduler) reads the pump `url` **and** `autoOffMinutes` from `settingsStore`, so the client posts only `{ state }` to `/api/v1/pump/control` and `GET /api/v1/pump/status` takes no `target` arg. The old build-time `VITE_PUMP_URL` dev tunnel is retired — set `PUMP_URL` in the backend's `.env` (`npm run dev` loads it via Node's native `--env-file`); see `DEV.md`.
- **Irrigation AUTO mode** (`src/scheduler/irrigationScheduler.js`): a real server-run watering scheduler (the pump firmware has no clock). The schedule lives in `settings.json` under `irrigation: { auto, timezone, moistureThreshold, entries[] }` (each entry `{ id, label?, start:"HH:MM", durationMinutes 1–60, days:[0..6], enabled }`), edited on the **Irrigation page** via `settingsApi`. The scheduler ticks every ~20 s, reads settings live, and fires any enabled entry whose `start` matches the current minute on today's weekday **in `timezone`** (computed with `Intl`, DST-safe; default `Asia/Bangkok`; picked from a dropdown on the Irrigation page — `client/src/features/irrigation/timezones.js` maps a Windows-style zone list to representative IANA zones so what's stored stays a valid `Intl` zone). Each fire is **moisture-guarded** (skip if avg `soil_moisture` ≥ `moistureThreshold`; run if no reading — fail-open) and **dedup'd** per day; **no catch-up** on missed minutes. A run turns the pump ON via `pumpControl` and ends through the **existing auto-off timer** armed with the entry's duration (one off-path; duration shares the 1–60 min safety bound). **AUTO/MANUAL is server-global** (`irrigation.auto`): in AUTO the schedule owns the pump, so `POST /api/v1/pump/control {state:"on"}` is refused with **409** (UI disables manual ON on the Irrigation page + dashboard card); manual **OFF** is always allowed as an emergency stop. Runtime status (`nextRun`/`lastRun`/`lastSkip`) is polled from `GET /api/v1/irrigation/status`.
- **Pump action log** (`src/store/pumpLog.js`): every actuation + decision is logged — manual ON/OFF, scheduled ON, auto-off firing, moisture-guard **skips**, and **failed** (unreachable) attempts — each `{ id, at, action:on|off|skip, source:manual|schedule|auto-off, ok, label?, durationMinutes?, moisture?, error?, note? }`. Logged centrally at the choke points: `pumpControl.command()` (on/off, threads `source`+`label`), `armTimer()`'s fired callback (auto-off), and the scheduler (skips). Stored as a bounded in-memory ring (default **500**, env `PUMP_LOG_MAX`) **atomically persisted** to `/data/pump-log.json` on each append (sparse writes; loaded at boot), so history survives restart. Writes are best-effort (never break actuation). Exposed at `GET /api/v1/irrigation/log?limit=N` (newest first), polled by the **Activity Log** panel on the Irrigation page. The 409-refused manual-ON in auto mode is *not* logged (no actuation occurred).
- **Build/version info** (Settings → **About / System Info**): `client/vite.config.js` bakes `{ version, buildNumber, gitSha, buildDate }` into the bundle at build time via Vite `define` (exposed through `src/lib/buildInfo.js`). Version = `client/package.json`; build number = `git rev-list --count HEAD`; SHA = `git rev-parse --short HEAD`; date = build clock (ISO-8601 UTC, rendered localized). Git is read directly when a `.git` is present (local dev / `npm run dev`), else it **falls back to env** (`BUILD_NUMBER`/`GIT_SHA`/`BUILD_DATE`) → `dev`/`unknown`/now. The Docker `client-build` stage has no `.git`, so `docker-compose.yaml` passes those as `build.args` from host env; `web-server/scripts/deploy.js` (`npm run deploy`) computes them from git on the host and runs compose — cross-platform (Node, not a shell one-liner, so it works from PowerShell).
- **AI frame-pull** (`docs/ai-frame-pull.md`): the AI inference container gets camera images by **HTTP-pulling** `GET /api/v1/camera/frame.jpg` — **no SD-card frame files** (frames stay in the RAM ring; honors no-SD-wear). That endpoint carries an `ETag` (= frame `seq`) + `Last-Modified` + `X-Frame-Seq` and answers `If-None-Match` with `304`, so the AI only infers on new frames; `/status` also exposes `seq`. The AI code lives in the top-level **`smartfarm-ai/`** project (see its README). Its container runs the prebuilt NVIDIA DLI image `nvcr.io/nvidia/dli/dli-nano-ai:v2.0.2-r32.7.1`, joins the base compose's `smartfarm-net` bridge, and reaches the server at `http://web-server:3000`. Because it needs `runtime: nvidia` (Jetson-only), it lives in the **overlay** `smartfarm-ai/docker-compose.ai.yaml`, keeping the base dev-PC-safe. `smartfarm-net` has an explicit name in the base and is `external` in the overlay, so the two run as independent commands on the Jetson (base first — it creates the network — then the overlay): `cd web-server && docker compose -f docker-compose.yaml up -d` then `cd ../smartfarm-ai && docker compose -f docker-compose.ai.yaml up -d`. Reference notebook + poller are in `smartfarm-ai/`. Frames are bounded by the camera's push cadence (no on-demand capture — lower `snapshot_interval_ms` in Settings for a faster rate).
- **AI service architecture** (`smartfarm-ai/`): all AI **decision** logic is separated into the `smartfarm-ai` container so the web-server stays AI-agnostic (it owns data, settings, history, UI, and *calls* the AI). `smartfarm-ai/ai_service.py` is a tiny **stdlib** `http.server` (no pip deps, Py3.6) run as the container command (`entrypoint: python3 ai_service.py` — JupyterLab is no longer the default; launch it ad-hoc for model dev). Endpoints: `GET /health`, `POST /water-stress` (`{inputs,thresholds}`→`{band,risk,factors}`, logic in `smartfarm-ai/water_stress.py`). Future vision features (canopy/disease) add endpoints here. The web-server reaches it at `http://smartfarm-ai:8000` (`AI_SERVICE_URL`). Trade-off: an AI feature now **requires the smartfarm-ai container** (Jetson-only) and degrades to "AI offline" otherwise.
- **Water Stress Estimation** (feature 1 of `docs/ai-features-roadmap.md`): a real **rule-based** advisory (no ML) — risk `low|medium|high|unknown`. **The decision now lives in the `smartfarm-ai` container**, not the web-server: `src/insights/waterStress.js` is the ORCHESTRATOR — it averages **fresh** sensor telemetry (soil required, per `lastSeen` within `WATER_STRESS_STALE_MS`; temp/humidity optional), then POSTs `{inputs, thresholds}` to the AI decision service (`AI_SERVICE_URL`, default `http://smartfarm-ai:8000/water-stress`) which returns `{band, risk, factors}` (soil bands + hot&dry/cool&humid adjust — the port lives in `smartfarm-ai/water_stress.py`). Web-server keeps aggregation, **smoothing** (band ring), **history**, settings, caching. A ~30s **tick** calls the AI, caches the result (with an `aiOnline` flag), and appends a **persisted** history point every ~5 min to `/data/water-stress-history.json`; `GET /api/v1/water-stress` (current) + `/history` serve the cache. **Graceful degrade, no local fallback:** if the AI service is unreachable, the last-known result is served marked `aiOnline:false` (or `unknown` if never computed) — the UI (`WaterStressCard`, `AiInsightsPage`) shows an **AI OFFLINE** indicator. Thresholds live in `settings.json` under `waterStress` (validated in `settingsStore`, Settings-page panel). **Advisory only** — never actuates the pump. This **replaced the fabricated analytics simulator** (old `/analytics` route/slice/api + `AiInsightCard` removed); `/analytics`→`/insights` is a real **AI Insights** page, the future home for the roadmap's vision features.
- **Canopy Coverage** (feature 2 of `docs/ai-features-roadmap.md`): % green-pixel cover via **classical HSV thresholding** (no model) — the first *vision* insight. Same **orchestrator** pattern as water stress: `src/insights/canopy.js` grabs the latest RAM frame (`frameStore`), POSTs the JPEG + HSV thresholds (query) to `POST /canopy` on `smartfarm-ai` (`CANOPY_SERVICE_URL`; logic in `smartfarm-ai/canopy.py`, PIL+numpy: downscale → hue/sat/val mask → `{canopyPercent, factors, maskPng}`), smooths, caches, persists history (`/data/canopy-history.json`), degrades (`aiOnline`). No fresh frame (older than `CANOPY_FRAME_STALE_MS`) → `unknown`. Endpoints: `GET /api/v1/canopy` (light), `/canopy/history`, `/canopy/preview.png` (the green-mask **preview**, RAM-only, for tuning). HSV thresholds in `settings.json` `canopy` (hue °, sat/val % — Settings panel, live-tunable while watching the mask on the **AI Insights** page, which shows a Canopy panel + trend). Advisory only.
- **Disease Detection** (feature 3 of `docs/ai-features-roadmap.md`): a pretrained **PlantVillage** CNN (default **MobileNetV2**, config-driven) — the first *model-based* insight, **on-demand only** (inference is heavy, so no tick). AI: `smartfarm-ai/disease.py` (served by `POST /disease`, raw JPEG) is a config-driven loader (`models/model_config.json` + `disease.pth`, **torch imported lazily** on first call) → whole-frame 224 + ImageNet norm → softmax → top-k; **weights aren't committed** (gitignored `smartfarm-ai/models/`), and no weights → honest "model not loaded". Setup is two steps: `smartfarm-ai/download_model.sh` (curl the checkpoint + `class_names.json`; default `Daksh159/plant-disease-mobilenetv2` — torchvision MobileNetV2 / 38 classes / ImageNet norm) then `docker exec smartfarm-ai python3 /smartfarm-ai/convert_weights.py` (loads into torchvision MobileNetV2, re-saves a clean **legacy-format** `models/disease.pth`, writes `models/model_config.json` with the label order from `class_names.json`). Web-server `src/insights/disease.js` orchestrates: `analyze()` grabs the latest frame, POSTs to `DISEASE_SERVICE_URL`, applies `settings.disease.confidenceThreshold` + a `/healthy/`-label heuristic → headline (`Healthy` / `Possible: <disease>` / `Inconclusive` / `no frame` / `AI offline` / `model not loaded`), caches + appends a **persisted log** (`diseaseStore.js` → `/data/disease-log.json`). Routes: `GET /api/v1/disease` (last), `POST /api/v1/disease/analyze` (trigger, server de-dupes concurrent calls), `GET /api/v1/disease/history`. UI: a Disease panel on **AI Insights** (Analyze button, headline + top-3 + recent-checks) **and** a dashboard `DiseaseCard`. **Two inference backends**, selected by `model_config.json`'s `runtime` (inferred from the weights extension if absent), because the two deployment hosts can't share one: **`torch`** (`.pth`) on Jetson/x86, and **`tflite`** (`.tflite`) on the **32-bit Raspberry Pi** — PyTorch publishes *zero* `armv7l` wheels on PyPI (any version), so `import torch` can never succeed there, while `tflite-runtime` does ship them (`2.14.0`, the newest with a `cp311` `armv7l` wheel; its `manylinux_2_34` floor is met by bookworm's glibc 2.36 — installed by `smartfarm-ai/Dockerfile` with `--no-deps` so apt's prebuilt numpy/Pillow survive). The `.tflite` is produced **off-Pi** by `smartfarm-ai/convert_to_tflite.py` (torch → ONNX → `onnx2tf`, which does the NCHW→NHWC transpose; a hand-rolled Keras port would silently differ because torchvision pads symmetrically and Keras pads TF-style). It self-verifies by running both models on `models/leaf.jpg` and comparing logits. Also fixed: a failed load used to latch **permanently**, so dropping weights into `models/` did nothing until a container restart — `_ensure_loaded()` now retries after `DISEASE_RETRY_AFTER_S` (30 s). **The upstream label file is broken** (37 entries for a 38-class checkpoint: index 37 `Tomato___healthy` absent, index 36 mangled to `Tomato___Tomato_mosaic_Normally`); the converters used to pad with a synthetic `class_37`, which defeats the `/healthy/` headline match so a healthy tomato read as "Possible: class_37". `smartfarm-ai/verify_class_names.py` now validates/repairs it against the committed canonical `plantvillage_classes.json` and is run by `download_model.sh` **and** both converters, so a re-download can't reintroduce it; it only rewrites files it recognizes as PlantVillage (≥90% positional match), leaves other models alone, and rejects (rather than guesses at) a label file with holes. **Limitation:** PlantVillage wants single-leaf close-ups; wide ESP32-CAM shots read as low-confidence "inconclusive" — accuracy needs close-up framing or a crop-specific model (drop-in via `model_config.json`). Advisory only.
- Device state is in-memory only (a `Map` in `deviceStore.js`) — it resets on restart, by design, to avoid SD card wear on the Jetson.
- Not yet verified end-to-end (no `node`/`npm`/network access in the sandbox this was built in) — run the commands above on the target machine before trusting it.
