# Role
You are a Principal IoT Solutions Architect and Lead Full-Stack Developer specializing in Smart Agriculture (AgTech) infrastructure, multi-architecture Docker containerization for resource-constrained Edge hardware (NVIDIA Jetson Nano running Ubuntu 18.04), and modular React-Redux control dashboards.

# Context
I am building a foundational, centralized **Smart Farm Web Control Center** to ingest telemetry data from field sensors (soil moisture, temperature, etc.) and send remote commands down to actuators (valves, pumps, switches). 

The target deployment host is an older Jetson Nano (Ubuntu 18.04 LTS). Because system memory and CPU are highly constrained on this machine—and must be preserved for potentially heavy edge automation or local AI models—I cannot run an independent React development server at runtime. 

Instead, the entire system must be containerized using Docker, with the React frontend compiled into static assets ahead of time and served directly via a unified Node.js/Express server on a single network port. This initial version must act as a clean, highly generic blueprint that allows me to plug in new device types and features later.

# Architectural & Container Requirements

### 1. Multi-Stage Docker & Compose Layout
* **Dockerfile:** Create an optimized multi-stage build targeting an ARM64/Jetson Nano friendly runtime base (like `node:16-alpine` or `node:18-slim` compatible with Ubuntu 18.04 glibc baselines).
  * *Stage 1 (Build):* Installs frontend tools and compiles the React application into a static production folder (`dist` or `build`).
  * *Stage 2 (Runtime):* Drops heavy build tools, copies over the static frontend assets and backend code, installs production-only Node dependencies, and exposes a single unified web port.
* **docker-compose.yml:** Include a basic compose file configured for low resource environments, managing auto-restarts and simple port exposure.

### 2. Extensible Node.js Core Backend
* **Data Ingestion API:** Create a lightweight POST endpoint (`/api/v1/telemetry`) to process generic JSON payloads (e.g., `device_id`, `timestamp`, `metrics: {}`) in-memory to prevent hammering the Jetson's SD card storage.
* **Device Command API:** Create a POST endpoint (`/api/v1/control`) to receive a target device ID and an action payload, ready for distribution to field nodes.
* **Unified Hosting:** Configure `express.static()` to natively host the pre-built React asset directory, gracefully mapping SPA routing fallbacks to `index.html`.

### 3. Modular React & Redux Toolkit UI
* **Generic Dashboard Grid:** Provide a clean, grid-based dashboard that dynamically displays a collection of "Device Cards."
* **Scalable Redux Structure:** Design a generic `devicesSlice` that stores field devices as objects in a flexible dictionary. The state must dynamically update whether an incoming metric is recorded or an actuator switch is flipped.
* Use lightweight polling mechanisms (like standard React intervals or RTK Query fixed intervals) to pull field changes safely without causing memory leaks or UI freeze on the browser side.

# Constraints & Design Principles
* **Hardware Agnostic Data Schemas:** Treat field units as generic definitions (e.g., "Device_01" with a dictionary of reading keys) so adding completely new sensor types later requires zero code changes.
* **Zero Runtime Overhead:** Absolutely no developer tools, live-reload watchers, or independent dev servers are permitted to run in the background at production runtime.

## Commands

- Backend: `npm install && npm start` (serves on `PORT`, default 3000).
- Frontend dev: `cd client && npm install && npm run dev` (Vite dev server, proxies `/api` to `localhost:3000`).
- Frontend production build: `cd client && npm run build` → outputs `client/dist`, which `server.js` serves via `express.static`.
- Full container: `docker compose up --build` from `web-server/`.
- Deploy with real build metadata: `npm run deploy` from `web-server/` (wrapper computes git build number/SHA/date on the host and passes them as compose build args → the Settings **About** panel shows real values; plain `docker compose up --build` builds fine but falls back to `dev`/`unknown`).

## Notes

- `GET /api/v1/devices` was added beyond the original two endpoints since the dashboard needs a way to fetch current state to poll.
- `GET /api/v1/health` returns `{ status, uptime, deviceCount, timestamp }` and backs the `docker-compose.yaml` healthcheck. The healthcheck probes it with `node -e` (via `http.get`) rather than `curl`/`wget`, keeping the `node:18-alpine` image dependency-free.
- **ESP32-CAM camera feed** (`src/routes/camera.js` + `src/store/frameStore.js`): the camera firmware's PUSH mode POSTs raw `image/jpeg` to `POST /api/v1/camera/frame`; the server keeps only the **latest** frame in a single-slot in-memory buffer (no SD writes) and exposes `GET /frame.jpg` (snapshot), `GET /stream` (multipart/x-mixed-replace MJPEG relay of the *pushed* frames — all viewers share the one buffer), and `GET /status`. Uses the built-in `express.raw()` — no new npm deps. Tunables: `CAMERA_MAX_FRAME_BYTES`, `CAMERA_STALE_MS`. On the camera side set `PUSH_ENABLED 1` and `PUSH_URL "http://<jetson-ip>:3000/api/v1/camera/frame"` in `include/secrets.h`.
- **Live video proxy** (`src/routes/camera.js` `GET /live` + `src/store/cameraLive.js`): the PUSH path above is ~1 frame/10s (a slideshow), and the camera's own high-fps `:81/stream` is only reachable from the camera's Wi-Fi subnet — so a browser viewing the deployed dashboard from elsewhere gets a black feed. `GET /api/v1/camera/live` fixes this: the server (on the camera's network) pulls the camera's `:81` MJPEG **once** and fans it out to all viewers **same-origin**, so any client that can load the dashboard sees live video and the camera serves a single connection (dodging its tiny concurrent-stream limit). Camera source via `CAMERA_STREAM_URL` env (default `http://192.168.0.3:81/stream`); auto-reconnects on transient drops, ends viewers on hard-down (page shows NO SIGNAL). The client's **relay** camera mode (now the default in `cameraSettings.js`) streams from `/api/v1/camera/live`; **custom** mode points the browser straight at a camera URL (needs direct reachability).
- **Server-owned dashboard settings** (`src/store/settingsStore.js` + `src/routes/settings.js`): the Settings-page **Camera Source** and **Pump Control** blocks used to live per-browser in `localStorage`; they are now **global, server-owned config** persisted to `data/settings.json` (atomic temp+rename write, on the same host volume as `camera-config.json`). `GET /api/v1/settings` returns the whole `{ cameraSource, pump }`; `POST` takes a **partial patch** (just the edited section), validates server-side (pump `url` must be http(s) since the server fetches it, `autoOffMinutes` 1–60, `sourceMode` = `relay|custom`), deep-merges, and returns the full object. Defaults are **env-seeded** (`PUMP_URL`, `PUMP_LABEL`, `PUMP_AUTO_OFF_MINUTES`, `CAMERA_SOURCE_MODE`/`_STREAM_URL`/`_SNAPSHOT_URL`, `SETTINGS_PATH`) and loaded at boot (`settingsStore.load()`). The client reads it via RTK Query (`settingsApi`, fetch-on-mount + `refetchOnFocus`/`refetchOnReconnect`, no polling; save invalidates the cache). `usePumpSettings()`/`useCameraSettings()` keep their names/shapes as thin wrappers over that query. **Camera device config (`camera-config.json`) is deliberately left separate** — it's a firmware-pulled contract, not dashboard settings.
- **Pump target is now server-owned:** the shared pump command layer (`src/store/pumpControl.js`, used by both the route and the scheduler) reads the pump `url` **and** `autoOffMinutes` from `settingsStore`, so the client posts only `{ state }` to `/api/v1/pump/control` and `GET /api/v1/pump/status` takes no `target` arg. The old build-time `VITE_PUMP_URL` dev tunnel is retired — set `PUMP_URL` in the backend's `.env` (`npm run dev` loads it via Node's native `--env-file`); see `DEV.md`.
- **Irrigation AUTO mode** (`src/scheduler/irrigationScheduler.js`): a real server-run watering scheduler (the pump firmware has no clock). The schedule lives in `settings.json` under `irrigation: { auto, timezone, moistureThreshold, entries[] }` (each entry `{ id, label?, start:"HH:MM", durationMinutes 1–60, days:[0..6], enabled }`), edited on the **Irrigation page** via `settingsApi`. The scheduler ticks every ~20 s, reads settings live, and fires any enabled entry whose `start` matches the current minute on today's weekday **in `timezone`** (computed with `Intl`, DST-safe; default `Asia/Bangkok`; picked from a dropdown on the Irrigation page — `client/src/features/irrigation/timezones.js` maps a Windows-style zone list to representative IANA zones so what's stored stays a valid `Intl` zone). Each fire is **moisture-guarded** (skip if avg `soil_moisture` ≥ `moistureThreshold`; run if no reading — fail-open) and **dedup'd** per day; **no catch-up** on missed minutes. A run turns the pump ON via `pumpControl` and ends through the **existing auto-off timer** armed with the entry's duration (one off-path; duration shares the 1–60 min safety bound). **AUTO/MANUAL is server-global** (`irrigation.auto`): in AUTO the schedule owns the pump, so `POST /api/v1/pump/control {state:"on"}` is refused with **409** (UI disables manual ON on the Irrigation page + dashboard card); manual **OFF** is always allowed as an emergency stop. Runtime status (`nextRun`/`lastRun`/`lastSkip`) is polled from `GET /api/v1/irrigation/status`.
- **Pump action log** (`src/store/pumpLog.js`): every actuation + decision is logged — manual ON/OFF, scheduled ON, auto-off firing, moisture-guard **skips**, and **failed** (unreachable) attempts — each `{ id, at, action:on|off|skip, source:manual|schedule|auto-off, ok, label?, durationMinutes?, moisture?, error?, note? }`. Logged centrally at the choke points: `pumpControl.command()` (on/off, threads `source`+`label`), `armTimer()`'s fired callback (auto-off), and the scheduler (skips). Stored as a bounded in-memory ring (default **500**, env `PUMP_LOG_MAX`) **atomically persisted** to `/data/pump-log.json` on each append (sparse writes; loaded at boot), so history survives restart. Writes are best-effort (never break actuation). Exposed at `GET /api/v1/irrigation/log?limit=N` (newest first), polled by the **Activity Log** panel on the Irrigation page. The 409-refused manual-ON in auto mode is *not* logged (no actuation occurred).
- **Build/version info** (Settings → **About / System Info**): `client/vite.config.js` bakes `{ version, buildNumber, gitSha, buildDate }` into the bundle at build time via Vite `define` (exposed through `src/lib/buildInfo.js`). Version = `client/package.json`; build number = `git rev-list --count HEAD`; SHA = `git rev-parse --short HEAD`; date = build clock (ISO-8601 UTC, rendered localized). Git is read directly when a `.git` is present (local dev / `npm run dev`), else it **falls back to env** (`BUILD_NUMBER`/`GIT_SHA`/`BUILD_DATE`) → `dev`/`unknown`/now. The Docker `client-build` stage has no `.git`, so `docker-compose.yaml` passes those as `build.args` from host env; `web-server/scripts/deploy.js` (`npm run deploy`) computes them from git on the host and runs compose — cross-platform (Node, not a shell one-liner, so it works from PowerShell).
- **AI frame-pull** (`docs/ai-frame-pull.md`): the AI inference container gets camera images by **HTTP-pulling** `GET /api/v1/camera/frame.jpg` — **no SD-card frame files** (frames stay in the RAM ring; honors no-SD-wear). That endpoint carries an `ETag` (= frame `seq`) + `Last-Modified` + `X-Frame-Seq` and answers `If-None-Match` with `304`, so the AI only infers on new frames; `/status` also exposes `seq`. The AI code lives in the top-level **`smartfarm-ai/`** project (see its README). Its container runs the prebuilt NVIDIA DLI image `nvcr.io/nvidia/dli/dli-nano-ai:v2.0.2-r32.7.1`, joins the base compose's `smartfarm-net` bridge, and reaches the server at `http://web-server:3000`. Because it needs `runtime: nvidia` (Jetson-only), it lives in the **overlay** `smartfarm-ai/docker-compose.ai.yaml`, keeping the base dev-PC-safe. `smartfarm-net` has an explicit name in the base and is `external` in the overlay, so the two run as independent commands on the Jetson (base first — it creates the network — then the overlay): `cd web-server && docker compose -f docker-compose.yaml up -d` then `cd ../smartfarm-ai && docker compose -f docker-compose.ai.yaml up -d`. Reference notebook + poller are in `smartfarm-ai/`. Frames are bounded by the camera's push cadence (no on-demand capture — lower `snapshot_interval_ms` in Settings for a faster rate).
- **AI service architecture** (`smartfarm-ai/`): all AI **decision** logic is separated into the `smartfarm-ai` container so the web-server stays AI-agnostic (it owns data, settings, history, UI, and *calls* the AI). `smartfarm-ai/ai_service.py` is a tiny **stdlib** `http.server` (no pip deps, Py3.6) run as the container command (`entrypoint: python3 ai_service.py` — JupyterLab is no longer the default; launch it ad-hoc for model dev). Endpoints: `GET /health`, `POST /water-stress` (`{inputs,thresholds}`→`{band,risk,factors}`, logic in `smartfarm-ai/water_stress.py`). Future vision features (canopy/disease) add endpoints here. The web-server reaches it at `http://smartfarm-ai:8000` (`AI_SERVICE_URL`). Trade-off: an AI feature now **requires the smartfarm-ai container** (Jetson-only) and degrades to "AI offline" otherwise.
- **Water Stress Estimation** (feature 1 of `docs/ai-features-roadmap.md`): a real **rule-based** advisory (no ML) — risk `low|medium|high|unknown`. **The decision now lives in the `smartfarm-ai` container**, not the web-server: `src/insights/waterStress.js` is the ORCHESTRATOR — it averages **fresh** sensor telemetry (soil required, per `lastSeen` within `WATER_STRESS_STALE_MS`; temp/humidity optional), then POSTs `{inputs, thresholds}` to the AI decision service (`AI_SERVICE_URL`, default `http://smartfarm-ai:8000/water-stress`) which returns `{band, risk, factors}` (soil bands + hot&dry/cool&humid adjust — the port lives in `smartfarm-ai/water_stress.py`). Web-server keeps aggregation, **smoothing** (band ring), **history**, settings, caching. A ~30s **tick** calls the AI, caches the result (with an `aiOnline` flag), and appends a **persisted** history point every ~5 min to `/data/water-stress-history.json`; `GET /api/v1/water-stress` (current) + `/history` serve the cache. **Graceful degrade, no local fallback:** if the AI service is unreachable, the last-known result is served marked `aiOnline:false` (or `unknown` if never computed) — the UI (`WaterStressCard`, `AiInsightsPage`) shows an **AI OFFLINE** indicator. Thresholds live in `settings.json` under `waterStress` (validated in `settingsStore`, Settings-page panel). **Advisory only** — never actuates the pump. This **replaced the fabricated analytics simulator** (old `/analytics` route/slice/api + `AiInsightCard` removed); `/analytics`→`/insights` is a real **AI Insights** page, the future home for the roadmap's vision features.
- **Canopy Coverage** (feature 2 of `docs/ai-features-roadmap.md`): % green-pixel cover via **classical HSV thresholding** (no model) — the first *vision* insight. Same **orchestrator** pattern as water stress: `src/insights/canopy.js` grabs the latest RAM frame (`frameStore`), POSTs the JPEG + HSV thresholds (query) to `POST /canopy` on `smartfarm-ai` (`CANOPY_SERVICE_URL`; logic in `smartfarm-ai/canopy.py`, PIL+numpy: downscale → hue/sat/val mask → `{canopyPercent, factors, maskPng}`), smooths, caches, persists history (`/data/canopy-history.json`), degrades (`aiOnline`). No fresh frame (older than `CANOPY_FRAME_STALE_MS`) → `unknown`. Endpoints: `GET /api/v1/canopy` (light), `/canopy/history`, `/canopy/preview.png` (the green-mask **preview**, RAM-only, for tuning). HSV thresholds in `settings.json` `canopy` (hue °, sat/val % — Settings panel, live-tunable while watching the mask on the **AI Insights** page, which shows a Canopy panel + trend). Advisory only.
- **Disease Detection** (feature 3 of `docs/ai-features-roadmap.md`): a pretrained **PlantVillage** CNN (default **MobileNetV2**, config-driven) — the first *model-based* insight, **on-demand only** (inference is heavy, so no tick). AI: `smartfarm-ai/disease.py` (served by `POST /disease`, raw JPEG) is a config-driven loader (`models/model_config.json` + `disease.pth`, **torch imported lazily** on first call) → whole-frame 224 + ImageNet norm → softmax → top-k; **weights aren't committed** (gitignored `smartfarm-ai/models/`), and no weights → honest "model not loaded". Setup is two steps: `smartfarm-ai/download_model.sh` (curl the checkpoint + `class_names.json`; default `Daksh159/plant-disease-mobilenetv2` — torchvision MobileNetV2 / 38 classes / ImageNet norm) then `docker exec smartfarm-ai python3 /smartfarm-ai/convert_weights.py` (loads into torchvision MobileNetV2, re-saves a clean **legacy-format** `models/disease.pth`, writes `models/model_config.json` with the label order from `class_names.json`). Web-server `src/insights/disease.js` orchestrates: `analyze()` grabs the latest frame, POSTs to `DISEASE_SERVICE_URL`, applies `settings.disease.confidenceThreshold` + a `/healthy/`-label heuristic → headline (`Healthy` / `Possible: <disease>` / `Inconclusive` / `no frame` / `AI offline` / `model not loaded`), caches + appends a **persisted log** (`diseaseStore.js` → `/data/disease-log.json`). Routes: `GET /api/v1/disease` (last), `POST /api/v1/disease/analyze` (trigger, server de-dupes concurrent calls), `GET /api/v1/disease/history`. UI: a Disease panel on **AI Insights** (Analyze button, headline + top-3 + recent-checks) **and** a dashboard `DiseaseCard`. **Two inference backends**, selected by `model_config.json`'s `runtime` (inferred from the weights extension if absent), because the two deployment hosts can't share one: **`torch`** (`.pth`) on Jetson/x86, and **`tflite`** (`.tflite`) on the **32-bit Raspberry Pi** — PyTorch publishes *zero* `armv7l` wheels on PyPI (any version), so `import torch` can never succeed there, while `tflite-runtime` does ship them (`2.14.0`, the newest with a `cp311` `armv7l` wheel; its `manylinux_2_34` floor is met by bookworm's glibc 2.36 — installed by `smartfarm-ai/Dockerfile` with `--no-deps` so apt's prebuilt numpy/Pillow survive). The `.tflite` is produced **off-Pi** by `smartfarm-ai/convert_to_tflite.py` (torch → ONNX → `onnx2tf`, which does the NCHW→NHWC transpose; a hand-rolled Keras port would silently differ because torchvision pads symmetrically and Keras pads TF-style). It self-verifies by running both models on `models/leaf.jpg` and comparing logits. Also fixed: a failed load used to latch **permanently**, so dropping weights into `models/` did nothing until a container restart — `_ensure_loaded()` now retries after `DISEASE_RETRY_AFTER_S` (30 s). **The upstream label file is broken** (37 entries for a 38-class checkpoint: index 37 `Tomato___healthy` absent, index 36 mangled to `Tomato___Tomato_mosaic_Normally`); the converters used to pad with a synthetic `class_37`, which defeats the `/healthy/` headline match so a healthy tomato read as "Possible: class_37". `smartfarm-ai/verify_class_names.py` now validates/repairs it against the committed canonical `plantvillage_classes.json` and is run by `download_model.sh` **and** both converters, so a re-download can't reintroduce it; it only rewrites files it recognizes as PlantVillage (≥90% positional match), leaves other models alone, and rejects (rather than guesses at) a label file with holes. **Limitation:** PlantVillage wants single-leaf close-ups; wide ESP32-CAM shots read as low-confidence "inconclusive" — accuracy needs close-up framing or a crop-specific model (drop-in via `model_config.json`). Advisory only.
- Device state is in-memory only (a `Map` in `deviceStore.js`) — it resets on restart, by design, to avoid SD card wear on the Jetson.

# ESP32 Firmware Projects

The repo also contains firmware for the field devices that talk to the web-server:

- `esp-idf-iot/` — the reference **ESP-IDF** workspace (`web-server/` SoftAP+HTTP+OTA control server, `sensor-node/`, and `examples/`). GPL-3.0. The canonical smart-farm firmware; the projects below borrow its conventions.
- `esp32cam/` — **PlatformIO / Arduino** firmware for the AI-Thinker ESP32-CAM that pushes JPEG frames to the web-server's `/api/v1/camera/frame` (see the camera notes above). Uses a gitignored `include/secrets.h` (+ `secrets.example.h`) for WiFi/OTA creds.
- `ap-server/` — **PlatformIO / Arduino** firmware for an **ESP-WROOM-32** (`board = esp32dev`) that runs a Wi-Fi **SoftAP with a custom DHCP server** supporting **MAC→IP reservations** managed from a **web UI** and persisted in NVS. Grew out of the AP behavior of `esp-idf-iot/web-server` (ESP-IDF), re-implemented on Arduino to match `esp32cam`'s conventions.
- `sensor-zone/` — **PlatformIO / ESP-IDF** port of `esp-idf-iot/sensor-node` for an **ESP-WROOM-32** (`board = esp32dev`) mapped to a farm zone: reads DHT22 + soil-moisture ADC and POSTs telemetry to the Node web-server. A faithful `framework = espidf` port (not Arduino — the source is 100% IDF-native) using the **pioarduino** platform fork (IDF 5.3.x). Uses a gitignored `include/secrets.h` (+ `secrets.example.h`) to match `esp32cam`/`ap-server` conventions.
- `pump-zone/` — **PlatformIO / ESP-IDF** port of `esp-idf-iot/web-server` for an **ESP-WROOM-32** (`board = esp32dev`) — the **actuator counterpart to `sensor-zone`**: joins the AP as a STA and runs an `esp_http_server` that switches an **irrigation-pump relay** on command, showing status on an **RGB LED**. A deliberately *stripped + modernized* port keeping **only** relay control + LED status (drops the source's SoftAP provisioning, web UI, OTA, RTC/SNTP, sensor cache, and automatic irrigation). `framework = espidf` via the **pioarduino** fork (IDF 5.3.x); gitignored `include/secrets.h` (+ `secrets.example.h`).
- `pump-zone-esp01/` — **PlatformIO / Arduino** firmware for an **ESP-01/01S (ESP8266EX**, `board = esp01_1m`) — a **drop-in replacement for `pump-zone`** on cheaper ESP8266 hardware. Same role, same `DEVICE_ID` (`pump_zone_01`), same `/api/v1/relay` contract, so the hub/dashboard need zero changes. **Necessarily a rewrite, not a port:** ESP-IDF has no ESP8266 target, so it's rebuilt on the Arduino stack (`ESP8266WebServer` + ArduinoJson + `ESP8266WiFi` auto-reconnect). Adds a **local safety cutoff** (dead-man timer), a **device watchdog** (`src/watchdog.{cpp,h}` — SW/HW watchdog feed for acute loop hangs + a lost-link recovery layer that forces the pump OFF and reboots if WiFi stays down past `WIFI_RECOVER_MS`), and **ArduinoOTA**; collapses the RGB LED to single-LED blink codes. Note: this is the one **ESP8266** project despite the "ESP32 Firmware Projects" heading. Gitignored `include/secrets.h` (+ `secrets.example.h`).
- `water-temp-node/` — **PlatformIO / Arduino (STM32duino)** firmware for a **NUCLEO-WL55JC1** (STM32WL55JC, `board = nucleo_wl55jc`, `framework = arduino`, flash via onboard/external **ST-Link**). A **battery-powered LoRa** multi-probe **water-temperature** (up to 6) + **air/CO2** sensor node — the repo's **first non-ESP, first LoRa, first sub-GHz** device. **Why `arduino` not `stm32cube`:** PlatformIO's ststm32 platform has **no** stm32cube framework for the STM32WL family (no `framework-stm32cubewl` package exists in the official *or* maxgerhardt platforms; the WL board advertises only `arduino`/`zephyr`). But **STM32duino *is* the STM32Cube HAL underneath**, so the intended HAL SubGHz driver compiles unchanged — we just enable `HAL_SUBGHZ` via `include/hal_conf_extra.h` (the STM32duino override hook). Every `WAKE_INTERVAL_S` (default 15 min) it wakes from **Stop2** (raw-HAL `HAL_PWREx_EnterSTOP2Mode` + RTC/LSE wake on the CM4 `RTC_WKUP_IRQn` — **not** the STM32LowPower lib, whose 2.0.0 release `#error`s against the core PlatformIO bundles), powers **6× DS18B20** (one per GPIO, SKIP-ROM, so they convert in PARALLEL — one 750 ms wait, not six; P0=PA5 P1=PA4 P2=PA9 P3=PC2 P4=PC1 P5=PB10) through an **A0341 P-MOSFET** high-side gate (PA8, active-low, whole rail incl. pull-ups; 100k gate pull-up = OFF while Hi-Z), reads both temps (12-bit, hand **bit-banged**, `ds18b20.cpp`, `delayMicroseconds` timing), reads **THREE SHT45s** (air temp/humidity, all I2C 0x44, behind a TCA9548A bus switch at 0x70 — see below) and an **SCD41** (CO2, I2C 0x62, upstream of the switch) on **PA11=SDA/PA12=SCL** off the *same* gated rail (gate = **PA8**, active-low), measures the battery via the internal **VREFINT** (STM32duino `analogRead(AVREF)`, no external parts; assumes battery *is* the 3.0–3.6 V rail), TX's **one uplink** (AS923 **923.2 MHz SF9BW125 CR4/5 14 dBm**), then sleeps. **Uplink-only** (never listens). It can't reach the HTTP web-server directly, so a **36-byte binary frame v5** (`src/lora/lora_packet.h`: magic/nodeId/seq/flags/probe0·probe1 int16 centi-°C/battery_mv/air_temp0·humidity0/pressure/co2/probe2..probe5/air_temp1·humidity1·air_temp2·humidity2/CRC-8) goes to **`lora-gateway/`**. **v4 (2026-08) widened the water temperatures from 2 probes to 6 and is purely additive**: probes 0/1 stay in v1's original two slots with their HOT/COLD flags, so v1/v2/v3 are byte-unchanged and an older two-probe node keeps working and keeps its metric names; probes 2-5 are appended after `co2`. **It adds no valid-flags and cannot** — all eight `flags` bits are spoken for (a v5 needing one must add a second flags byte) — so probes 2-5 signal 'no reading' with the existing `LORA_TEMP_INVALID` (0x8000) sentinel, and `lora_probe_valid()` in the shared header is the ONE place that knows probes 0/1 gate on a flag while 2-5 gate on the sentinel; node, gateway and the Python receiver all call it rather than testing either by hand. A probe that is not fitted needs no config change: an unconnected line sees no presence pulse, goes out as the sentinel, and is dropped by the gateway rather than appearing as a convincing 0.00 degC. **v5 (2026-08) then widened the air sensors from 1 SHT45 to 3**, same additive rule (v1-v4 byte-unchanged, air sensor 0 stays in the v2 slots with its AIR/HUM flags, sensors 1-2 appended after the probes and gated by sentinels — `LORA_TEMP_INVALID` for temperature and the new `LORA_HUM_INVALID` 0xFFFF for humidity, since %RH's valid range is 0..10000). `lora_air_valid()`/`lora_hum_valid()` are the air-side counterparts of `lora_probe_valid()`. Airtime grows ~41 ms per 8 bytes at SF9BW125 (20 B ~185 ms, 28 B ~226 ms, 36 B ~267 ms); the whole v3->v5 growth is ~4 mAs/wake — irrelevant beside the SCD41 — and costs no extra rail-on time at all. The LoRa driver (`src/lora/subghz_lora.c`, called from `main.cpp` via `extern "C"`) is a lean **self-contained SX126x command driver over `HAL_SUBGHZ`** — deliberately **not** the full CubeWL SubGHz_Phy middleware; RF-switch truth table (FE_CTRL1=PC4, FE_CTRL2=PC5, FE_CTRL3=PC3) + TCXO-on-DIO3 taken verbatim from ST's NUCLEO-WL55JC BSP. No `secrets.h` (raw LoRa needs no keys); config in committed `include/node_config.h`. Debug log on `Serial` (LPUART1 → ST-LINK VCP). **Verified: compiles clean** (`pio run`) — RAM 3.1%, Flash 15.4%. **DS18B20 bring-up test (`[env:bluepill_f103c8]`):** while the WL55 boards are on back-order, a second PlatformIO env reuses the **same `ds18b20.cpp`** (via `build_src_filter`, no copy) on an **STM32F103C8T6 Blue Pill** to validate the sensor + wiring — `src/test/ds18b20_test_main.cpp` reads two probes (hot=PB6, cold=PB7, direct 3V3, PC13 LED) and prints over **USB CDC** at ~1 Hz; `ds18b20.h` was made family-agnostic (`#include <Arduino.h>`) so it compiles on both targets. **Hardware-verified on the F103** (both probes track real, independent temperature). The F103 prototype grew several extra envs (all reusing the shipped drivers via `build_src_filter`, none affecting the WL55 build): **`[env:bluepill_f103c8_semihosting]`** — same DS18B20 test but output via **ARM semihosting over SWD** (`-DUSE_SEMIHOSTING`, `BKPT 0xAB`/`SYS_WRITE0`, viewed in the OpenOCD/VSCode Debug Console) for when a clone Blue Pill's native USB won't enumerate; **`-DDS18B20_INTERNAL_PULLUP`** uses the MCU's internal ~40k pull-up when no external 4.7k is on hand (short bench bus only); without it `ds18b20_init()` takes the `GPIO_NOPULL` path for an external resistor. Because that is a property of the **bench wiring**, not of a build, it is set in **one** place — `ds18b20_pullup` in `platformio.ini`'s `[bluepill_base]`, interpolated by every F103 env (the WL55 env never sets it — the real node always has its resistors). **Currently: external 4.7k per line, hardware-verified** reading both probes. A **`[env:bluepill_f103c8_dump]`** diagnostic env (+ `ds18b20_read_scratchpad()`) prints the raw 9-byte scratchpad and probes each DQ pin's idle level (internal pull-up vs pull-down) — `pull-up=1 pull-down=1` proves an external resistor is really on 3V3, `pull-up=0 pull-down=0` means the line is held low (resistor tied to GND / short), all-zero bytes mean a stuck-low bus. Added after a rewire held both DQ lines low. **`tools/watch.ps1`** wraps flash + semihosting-attach into one command (`tools/watch.ps1 [-PioEnv <env>] [-NoUpload]`), resolving pio/openocd under `~/.platformio` and killing a leftover openocd that would otherwise block the ST-Link. Also: `ds18b20_read()` now **rejects an all-zero scratchpad** (stuck-low bus passes CRC → fake 0.00 °C) — a fix that benefits the WL55 node too. **Long DS18B20 runs (10–20 m):** plain 1-Wire handles it (Maxim **AN148**) — **not** RS-485 (a MAX485 *cannot* sit on the 1-Wire line: it's a directional differential UART transceiver, 1-Wire is bidirectional open-drain reversing direction mid-bit-slot). Fit an **external ~2.2 kΩ** pull-up (not the internal ~40 kΩ; drop `DS18B20_INTERNAL_PULLUP`), **twisted-pair DQ+GND**, keep 3-wire VDD power; no firmware timing change. Escalate to a **DS2483/DS2480B** 1-Wire line-driver IC (active pull-up), or a remote MCU digitizing + RS-485/Modbus, only past ~30 m. See `water-temp-node/README.md` "Long DS18B20 runs". **Real-hardware design (`water-temp-node/docs/hardware-interface.md`):** the spec for the non-breadboard build, fixed as **two PCBs joined by a CABLE** — the NUCLEO-WL55JC1 (brain) + a **large custom front-end PCB** sitting beside it (the connector decision is spelled out below). Earlier never-built revisions of this spec (a morpho-stacking board, then an ARDUINO shield) have been **deleted from the doc** — if you meet a stale reference to `PB2`, `DQ_HOT`/PA10 or CN5/CN8 pin numbers anywhere, it is dead config, not an alternative. **Twelve signals** cross the joint (`VBAT`/2x`GND`/`SENS_GATE` PA8 active-low/`DQ_P0..P5`/`I2C_SDA`/`I2C_SCL`); `VSENS` (the gated rail) is generated on the front-end and never crosses back. **The three SHT45s add ZERO signals**, which is why they are arranged the way they are: the SHT4x I2C address is fixed at the factory by the order code (`SHT45-AD1B` = 0x44, no address pin), so three cannot share a bus — and **individually power-gating them does not work**, which is the trap worth remembering. An unpowered SHT45 still clamps SDA/SCL to its own VDD through its ESD diodes, so the 4.7k bus pull-ups phantom-power it to ~2.7 V (the part runs from 1.08 V) and it answers at 0x44 anyway; no pull-down value escapes it (10k leaves it alive at ~1.8 V, 1k kills it but clamps SDA to ~1.1 V, under the 2.31 V VIH). **What has to be switched is the BUS, not the power** — hence a **TCA9548A** (`src/tca9548a.{h,cpp}`, one channel at a time), which is itself an I2C device and so costs no pins and no connector signals. The SCD41 (0x62) collides with nothing and sits UPSTREAM of the switch. Sensor index = mux channel = frame slot = dashboard metric (`I2C_MUX_CHANNELS` in `node_config.h`); three identical 0x44 parts are otherwise indistinguishable, so the channel number is silkscreened next to each. Each downstream channel needs its OWN 4.7k pull-ups (the mux passes signals, not pull-ups). `main.cpp` hides all of it behind one `sht45_select(i)`. Front-end schematic + BOM (2.2k pull-ups **on the switched rail** so a gated-off probe can't leak, 100R series, low-C TVS, `VSENS` bulk bounded by the 10 ms `DS_POWER_SETTLE_MS`), the two Nucleo battery traps (ST-LINK draws mA — snap it off or feed 3V3 direct; **DS18B20 needs ≥3.0 V** so 2×AA alkaline is out, LiFePO4/lithium-AA in), and a bring-up order. Note `battery_read_mv()` (VREFINT) is only valid while the battery *is* VDDA — inserting a regulator breaks it. **`[env:bluepill_f103c8_sx1278]`** — bench self-test of an **external SX1278 (SX127x) LoRa module** (`src/sx1278.{h,cpp}`, Arduino SPI; a *different* chip/registers from the WL55's internal SX126x): SPI probe (RegVersion==0x12) → 433 MHz SF9/BW125 TX beacon; **hardware-verified** (RegVersion OK + TxDone). **`[env:bluepill_f103c8_node]`** — the full prototype **node**: DS18B20 → the shared **12-byte `lora_packet.h`** frame → SX1278 TX @433 (NSS=PA4 SCK=PA5 MISO=PA6 MOSI=PA7 RESET=PB0 DIO0=PB1); **hardware-verified** (reads probes + TxDone). This F103+SX1278 node is the 433 MHz prototype that pairs with **`lora-pi-receiver/`** (SX1278 = 433 MHz, so it does **not** reach the 923 MHz WL55 gateway — separate prototype path while the WL55 boards are on back-order). **`[env:bluepill_f103c8_node_standalone]`** is the same node **without** semihosting so it runs autonomously on any USB/battery power (the semihosting `BKPT` faults with no debugger attached; `out()` falls back to a harmless UART `Serial`) — flash it once and just power the board. **End-to-end HARDWARE-VERIFIED (2026-08):** F103 node → SX1278 433 → Pi SX1278 (SPI) → `lora-pi-receiver/receiver.py` → web-server accepted (HTTP 2xx), dashboard `water-temp-01` `temp_hot`/`temp_cold` matched the node exactly at RSSI ≈ −64 dBm / SNR ≈ 13 dB. **BME280 added (2026-08):** the node envs also read a **BME280 on I²C2 (PB10=SCL/PB11=SDA — I²C1/PB6-7 is the DS18B20 bus)** via the Adafruit BME280 lib and send **ambient air_temp/humidity/pressure** in an **18-byte frame v2** (magic `0xA2`). `lora_packet.h` gained v2 **additively** (`lora_packet_pack_v2`, new flags/fields) — **v1/12-byte is unchanged so the WL55 923 MHz path is untouched**; only the F103+BME280 433 path sends v2. `lora-pi-receiver/lora_packet.py` decodes **both** v1 and v2; `receiver.py` adds `air_temp`/`humidity`/`pressure` metrics. **SHT45 + SCD41 added (2026-08):** the node gained two more I²C sensors — a **SHT45** (air temp/humidity, 0x44) and a **Sensirion SCD41** (true photoacoustic NDIR **CO2**, 0x62) — on **both** the WL55 node and the F103 prototype, in a **20-byte frame v3** (magic `0xA3`) that appends `co2` to v2's layout; **v1/v2 are byte-unchanged**, and `lora_packet_unpack()` now accepts all three so an older node keeps working. Drivers are **hand-rolled from the datasheets** (`src/sht45.{cpp,h}`, `src/scd41.{cpp,h}`) over a shared `src/sensirion_i2c.{cpp,h}` helper (Sensirion word protocol: 16-bit BE words each followed by **CRC-8 poly 0x31/init 0xFF** — deliberately *not* the frame's `lora_crc8`, poly 0x07/init 0x00) — no vendor library, so the WL55 env still has **zero `lib_deps`**. **SHT45 supersedes the BME280 for air temp/humidity** (±0.1 °C/±1 %RH beats it); the BME280 keeps `pressure` only, and `LORA_FLAG_SHT` (bit 7) records which part supplied T/RH — same units either way, so it is *not* emitted as a metric (dashboard history stays continuous) but is logged once per node by `receiver.py`, and again only on change. **Two CO2 modes, because the hosts differ:** the mains-powered F103 runs the SCD41 **periodic** (free-running 5 s, cell stays warm, more accurate) and feeds the BME280 pressure back via `scd41_set_ambient_pressure()` (~1 % of reading per 10 hPa); the battery WL55 uses **single-shot** — 5 s per shot, and since the datasheet's first shot after power-up is unsettled, **two** shots (`CO2_SINGLE_SHOT_WARMUP`) ≈ 10 s of sensor-on time. That makes CO2 the node's dominant energy cost, so it is paced by `CO2_EVERY_N_WAKES` (default **4** → one reading/hour at the 15-min wake, a **0.28 %** duty cycle vs 1.1 %), re-sending the cached value in between with the flag still set. WL55 pins: **I2C2 PA11=SDA/PA12=SCL** (I2C1 wants PA9/PA10 = the probes; I2C3 wants PB11 = the Nucleo's **LED3**), both parts on the **same gated VSENS rail** as the probes — `sensor_pins_park()` now parks the I2C pins analog too, and `I2C_POWER_SETTLE_MS` (1000 ms, the SCD41's power-up time) is **overlapped** with the DS18B20 conversion so the rail is on for the longer of the two, not the sum. `docs/hardware-interface.md` updated: the connector contract grew from **six signals to eight** (+SDA/SCL) and then to **twelve** (+four more probe lines — **older front-end boards are not forward-compatible at any of these steps**), the SCD41's **~205 mA peaks** now size Q1 and the rail bulk/traces, and the enclosure must be **vented** (a sealed box measures its own interior's CO2). **The front-end is now a LARGE CUSTOM PCB joined by a CABLE, not a shield and not a morpho-stacking board** (switched 2026-08, after the ARDUINO-shield revision it replaces): six probe connectors + the two I2C parts + protection + battery input do not fit a 68.6×53.4 mm Uno outline, and once the board must be its own size the shield's only advantage (free keying from the outline) is gone anyway. **Two cables, deliberately split:** all **12** logic signals ride ONE 2×19 IDC ribbon on **morpho CN10** (`SENS_GATE`(**PA8**)→CN10-16, `DQ_P0..P5`→CN10-11/17/19/21/23/25, `I2C_SDA`(PA11)→CN10-5, `I2C_SCL`(PA12)→CN10-3, `GND`→CN10-9 **and** CN10-20), while battery power takes its **own keyed 2-pin lead** to **CN6-4/6/7**. Keeping `VBAT` off the ribbon is the point: a 2×19 socket on unshrouded morpho pins *can* be pressed on 180°-rotated, and with power split out the worst case is two open-drain GPIOs shorted to ground instead of battery voltage on a GPIO. **Keying is a physical stop, not a silkscreen arrow:** clip the **CN10-6** pin (it is NC) and plug the matching IDC hole — rotated, that hole lands on populated pin 33 (PB12) and the socket will not seat. **Use full-length sockets** (2×19 over all of CN10, 1×8 over all of CN6 with only 4/6/7 wired) so neither can be fitted one position out. Ribbon ≤30 cm. **Probe pins are placed by ribbon adjacency, not convenience** — six bit-banged open-drain lines in one flat cable is the new SI problem, so each DQ sits next to a **GND (CN10-9/20)** or an **NC (6/10/18/24/34, groundable at the front-end end only, as a one-ended guard)**; every other conductor floats at the front-end. **`SENS_GATE` is PA8** (CN10-16, inside the DQ block, no boot strap so it resets floating and the 100k holds the rail off), and **PA10 is deliberately unused** — a fine 1-Wire pin, but on CN7, and one line does not justify a second ribbon. **The do-not-route list is real again** — cabling to the morpho puts PC3/PC4/PC5 (RF switch), PB0 (TCXO), PA13/PA14 (SWD), the VCP, AVDD/AGND, all three buttons (PA0/PA1/PC6) and all three LEDs (PB9/PB11/PB15) back in reach — but SWD *can* now be brought out to a debug header, which the shield could not. Caveat recorded in the doc: SCL at CN10-3 sits between the RF-switch conductors CN10-2/4, tolerable only because the firmware gates the sensor rail off **before** powering the radio, so I2C is never active while those switch — do not reorder that sequence in `main.cpp`. The verified **morpho CN7 map** is retained as **Appendix A** for bench probing (CN10 is now in the main text), including that **CN7-33 `VBAT` is the RTC backup pin, NOT a power input** (a trap the shield could not reach and this revision can), and that **Table 18 has an erratum** — CN10-37 is printed `PB6 / PA3` but is `PB7 / PA3` (PB6 is already at pin 35, PB7 appears nowhere in a table whose preamble says all I/Os are present, and the UM's own note says D0/D1 = PB6 **and** PB7). Also flagged: UM2592 Table 17 labels PA11/PA12 `I2C1_*` while STM32duino's `PeripheralPins.c` and Zephyr both say **I2C2** — harmless for the firmware (STM32duino resolves the instance from the pin map) but check RM0453 before any bare-HAL port. Compile-verified; Python decode **unit-tested** by `lora-pi-receiver/test_lora_packet.py`, whose vectors are generated by compiling the firmware's own `lora_packet.h` on the host (v1/v2/v3, negative temps, invalid-probe sentinel, every single-byte corruption). Flash sizes: WL55 15.5%, node 52.9%, standalone 55.0%, sx1278 25.4%, semihosting DS18B20 ~40%.
- `lora-gateway/` — **PlatformIO / Arduino (STM32duino)** firmware for a **second NUCLEO-WL55JC1** — the **RX-only counterpart to `water-temp-node`**. Same framework rationale as above. Listens continuously on the shared AS923 channel (shares the node's `src/lora/*` + `include/hal_conf_extra.h` as **byte-identical copies** — change both together), validates CRC-8, maps `node_id → device_id` (`include/gateway_config.h`; unknown → `water-node-<id>`), and prints **one JSON line per frame** out `Serial`/VCP (adding `rssi`/`snr`/`seq`; invalid temps omitted; `#`-prefixed diagnostic lines). Decodes **v1..v5** and emits whichever metrics the frame marks valid (`air_temp`/`humidity`/`pressure`/`co2` on top of the water temps + battery), asking `lora_probe_valid()` per probe because v4's extra probes carry validity as the `0x8000` sentinel rather than a flag bit — `flags` has no spare bits left. `LED_BUILTIN` blinks per RX. Its host companion **`lora-gateway/bridge/`** is a standalone **Node.js + `serialport`** forwarder (kept out of `web-server/` to keep it hardware-agnostic, like the AI poller): reads the gateway's `/dev/ttyACM0` (or `COMx`), validates, and POSTs each line to `/api/v1/telemetry` (`SERVER_URL`); auto-reconnects; needs Node ≥ 18 (global `fetch`); `.env` via `--env-file`. So the full path is **node (LoRa) → gateway (WL55, RX) → bridge.js (USB→HTTP) → web-server:3000**, no LoRaWAN/gateway-vendor stack. Dashboard shows `water-temp-01` with `temp_hot`/`temp_cold`/`temp_p2`..`temp_p5`/`air_temp`/`humidity`/`air_temp_2..3`/`humidity_2..3`/`battery_v`/`rssi`/`snr` — metric naming lives in `gw_probe_metric()`/`gw_air_metric()`/`gw_hum_metric()` (`include/gateway_config.h`), with probes 0/1 and air sensor 0 keeping their historic labels so existing dashboard history stays one continuous series. **Verified: compiles clean** (`pio run`) — RAM 1.9%, Flash 9.7%.
- `lora-pi-receiver/` — **Python** LoRa gateway that runs on the **Raspberry Pi** hosting the web-server: an **SX1278 on the Pi's SPI0** receives the node's LoRa frames directly and POSTs telemetry — a single-box alternative to the WL55 gateway + USB bridge, for the **433 MHz prototype path** (`F103+SX1278 node → Pi SX1278 → receiver.py → localhost:3000`). Standalone (like `lora-gateway/bridge` + the AI poller): **web-server unchanged**. `sx127x.py` is a Python port of the node's `sx1278.cpp` (spidev + gpiozero/lgpio; **not** the WL55's internal SX126x); `lora_packet.py` ports `lora_packet.h`'s **v1..v5** decode (`test_lora_packet.py` checks it against vectors generated by compiling the C header on the host — incl. the `crc8(0×11)==0` all-zero property); `receiver.py` does RX → decode → map `node_id → device_id` → POST (stdlib `urllib`, no `requests`). Deps `spidev`/`gpiozero`/`lgpio`; runs as a **systemd** service (`lora-pi-receiver.service`) on the host, POSTing to the Dockerized web-server on `localhost:3000`. Wiring: NSS=CE0/GPIO8, SCK=GPIO11, MISO=GPIO9, MOSI=GPIO10, **RESET=GPIO22, DIO0=GPIO25**, 3V3, antenna (`raspi-config` → SPI on). **Not yet run on Pi hardware** (spidev/gpiozero need a real Pi) — the packet decoder is unit-tested and the SX127x register sequence mirrors the node's validated `sx1278.cpp`. The 923 MHz WL55 gateway path stays as the separate AS923 option.

## ap-server/

```
ap-server/
├── platformio.ini      # env:esp32dev — espressif32 / arduino, single USB env, port auto-detect
├── README.md           # design decisions + try-it steps
├── .gitignore
├── include/
│   ├── ap_config.h     # AP + addressing + reservation tunables (committed, not secret)
│   ├── reservations.h  # NVS-backed MAC→IP store (API)
│   └── dhcp_server.h   # custom DHCP server (API)
└── src/
    ├── main.cpp        # SoftAP bring-up + web UI (dashboard, /edit, CRUD endpoints)
    ├── reservations.cpp# reservation store (Preferences/NVS) + parseMac/macToStr
    └── dhcp_server.cpp # DISCOVER/OFFER/REQUEST/ACK/NAK/RELEASE on UDP/67
```

- **AP-only** mode (no STA uplink), WPA2, standalone network (SSID `MJU-SmartFarm-AP-II`, password `password` — **change `AP_PASSWORD`**, `192.168.1.1`, ch 1, **max 10 clients**), deliberately distinct from the ESP-IDF reference AP (`MJU-SmartFarm-AP` @ `192.168.0.1`). All tunables in committed `include/ap_config.h`; no `secrets.h`.
- **Why a custom DHCP server:** the built-in ESP DHCP server (`dhcpserver.h`) exposes only a pool *range* (`dhcps_lease_t`) — **no MAC-based reservation API**, and its source is precompiled into the framework's lwIP lib so it can't be patched from PlatformIO. So `main.cpp` calls `esp_netif_dhcps_stop("WIFI_AP_DEF")` and `dhcp_server.cpp` runs our own on UDP/67, **polled from `loop()`** (single-threaded with `WebServer`, so the reservation table needs no locking).
- **Addressing:** `.1` = AP; **`.2`–`.99` reserved** (MAC→IP, the "server group"); **`.100`–`.109` dynamic** (`DHCP_POOL_FIRST_HOST` .. `+AP_MAX_CONNECTIONS-1`, guarded by `static_assert`). Reserved MAC → fixed IP; unknown MAC → dynamic lease (RAM table, reused per MAC, 2 h lease `DHCP_LEASE_SECS`).
- **Reservations** persist in NVS via `Preferences` (namespace `apres`, one blob of `{mac[6],octet,label[≤24]}`, cap `MAX_RESERVATIONS`=32); loaded in `reservations::begin()` at boot. Web UI: `/` dashboard (auto-refresh; connected clients w/ one-click **Reserve** prefilling MAC, + reservations table w/ **Delete**), `/edit` form (no refresh, so it isn't wiped mid-typing), `POST /api/reservations` (upsert, validates MAC + IP∈`.2`–`.99` + uniqueness), `POST /api/reservations/delete`. **No auth** — WPA2 is the gate. Changes apply on the device's **next DHCP renewal/reconnect**.
- Commands: `cd ap-server && pio run` / `pio run -t upload` / `pio device monitor` (115200). **Compiles clean on arduino-esp32 2.0.17 (esp32dev)** but the hand-rolled DHCP server is **not yet hardware-tested** — during first bring-up keep one client on a static `192.168.1.50` as a lifeline in case DHCP misbehaves.

│   ├── network/wifi_sta.{c,h}   # config #defines moved out to include/secrets.h
│   ├── sensors/{dht22,soil_moisture_adc,sensor_task}.{c,h}
│   └── http/http_client.{c,h}
├── test/                  # host-side Unity tests (pio test -e native)
│   ├── test_soil_map/     # voltage→percent mapping + clamp
│   ├── test_dht_checksum/ # DHT22 decode + checksum accept/reject
│   └── test_json_body/    # telemetry body shape == server contract
└── tools/parity_diff.py   # diffs sensor readings from two serial-log captures
```

- **Why `framework = espidf` (not Arduino):** the legacy source is 100% ESP-IDF-native (`esp_adc` oneshot+cali, `esp_http_client`, `esp_wifi`/`esp_netif`/`esp_event`, `nvs_flash`, IDF `driver/ledc`, `esp_efuse_mac`, `esp_rom_delay_us`). An Arduino port would be a rewrite of every module and would *break* signal parity, so the port keeps the C logic byte-for-byte and only changes the build wrapper + telemetry contract.
- **Why the pioarduino platform fork:** the code needs **IDF ≥ 5.2** (`ADC_ATTEN_DB_12` + `esp_adc/adc_oneshot`), which mainline `platformio/espressif32` doesn't ship. `platformio.ini` pins `https://github.com/pioarduino/platform-espressif32.git#53.03.13` (Arduino core 3.1.3 / **IDF 5.3.2**), matching the legacy IDF 5.3.1.
- **Layout:** the legacy `main/` is a *single* IDF component with subfolders, so it's flattened verbatim into `src/` with one adapted `src/CMakeLists.txt` (no `lib/` / `components/` split).
- **GPIO map (preserved exactly from the legacy build):** DHT22 data `GPIO32` (bit-banged); soil moisture `ADC1_CH6` = `GPIO34` @ `ADC_ATTEN_DB_12` (DRY 2800 mV → 0%, WET 1200 mV → 100%); RGB status LED via LEDC on `GPIO25/26/27` (active-high, 5 kHz, 8-bit, ch 0/1/2, timer 0); onboard status LED `GPIO2` (active-low, 500 ms blink). No I2C/SPI in use.
- **Telemetry contract changed on purpose:** the legacy firmware POSTed a *flat* body to the old ESP-IDF web-server (`192.168.0.1:80/sensor-update`). This port targets the **Node web-server** (`192.168.0.2:3000/api/v1/telemetry`), which **requires** a `metrics{}` object (else HTTP 400), so `http_client.c` nests the readings: `{"device_id":"…","metrics":{"temperature":…,"humidity":…,"soil_moisture":…}}` (timestamp omitted — no RTC; the server stamps it). Because the HTTP body deliberately differs from the legacy binary, **parity is verified on the physical-pin readings** (serial-log diff via `tools/parity_diff.py`), not on the wire payload.
- Commands: `cd sensor-zone && cp include/secrets.example.h include/secrets.h` (fill creds) → `pio run` / `pio run -t upload` / `pio device monitor` (115200) / `pio test -e native`. **Not yet compiled or hardware-verified** — the first `pio run` pulls the pioarduino platform + IDF 5.3.2 (slow, one-time); confirm `ADC_ATTEN_DB_12` resolves before trusting it.

├── platformio.ini        # env:esp32dev (espidf) via pioarduino IDF 5.3.x, single USB env
├── sdkconfig.defaults     # generic parity keys (esp32, single-app, 4MB, 160MHz, 100Hz, INFO)
├── CMakeLists.txt         # top-level IDF project file
├── README.md

├── include/
│   ├── pump_config.h     # COMMITTED hw contract: RELAY_GPIO/ACTIVE_LEVEL, RGB pins, PUMP_HTTP_PORT
│   ├── secrets.h         # gitignored — WIFI_STA_AP_SSID/PASSWORD, DEVICE_ID
│   └── secrets.example.h # committed placeholder template
└── src/                  # stripped/modernized subset of esp-idf-iot/web-server/main/
    ├── main.c  main.h  task_settings.h
    ├── CMakeLists.txt    # idf_component_register (+ "../include", REQUIRES json for cJSON)
    ├── actuators/relay.{c,h}   # single relay, on/off (manual_override + auto dropped)
    ├── actuators/rgb_led.{c,h} # LEDC RGB, color-by-id (pins from pump_config.h)
    ├── network/wifi_sta.{c,h}  # STA-only, reused verbatim from sensor-zone
    └── http/http_server.{c,h}, http_server_relay.c  # relay-only server + JSON handler
```

- **Role in the topology:** unlike `sensor-zone` (an HTTP *client* that POSTs telemetry up), pump-zone is an HTTP *server*. It joins `MJU-SmartFarm-AP-II` as a STA (creds from `secrets.h`), takes a **DHCP** lease, and listens on `PUMP_HTTP_PORT` (80). Give it a stable address by **reserving its MAC** in `ap-server`'s web UI (the `.2`–`.99` "server group"). The Node hub or a browser POSTs pump commands **to** it.
- **Why `framework = espidf` + pioarduino:** the source `esp-idf-iot/web-server` is 100% IDF-native (`esp_http_server`, `esp_wifi`/`esp_netif`/`esp_event`, `driver/ledc`, `nvs_flash`, cJSON). Same platform pin as the siblings (`#53.03.13` = Arduino core 3.1.3 / IDF 5.3.2).
- **Deliberately stripped:** kept only `relay.c`, `rgb_led.c`, the HTTP server core + relay handler, and `main.c`. **Dropped** from the source: SoftAP + provisioning web UI + embedded assets, `app_nvs`, `irrigation_ctrl` (automatic irrigation), `sensor_cache`, `water_config`, `time_sync`/`rtc_ds3231`, OTA, and the monitor/status/wifi HTTP handlers. WiFi is `sensor-zone`'s STA-only `wifi_sta.c` reused verbatim (matching its `APP_MSG_WIFI_*` event contract), not the source's dual AP+STA `wifi_app.c`.
- **HTTP API (modernized to a JSON body):** `POST /api/v1/relay` with `{"state":"on"|"off"}` → `{"relay_status":"ON"|"OFF"}`; `GET /api/v1/relay` returns the same. Parsed with the IDF-bundled **cJSON** (`REQUIRES json`, no new PlatformIO deps). This intentionally replaces the source's header-based `/relayControl.json` contract and drops the `manual_override`/`auto` concept (there's no auto controller left to hand back to).
- **GPIO map:** relay (pump) on `GPIO2` **active-low** (matches the legacy `esp-idf-iot/web-server` wiring — the physical relay IN is on `GPIO2`; polarity + pin in `include/pump_config.h`). `GPIO2` is a boot **strapping** pin and idles HIGH when the pump is OFF, so if a USB flash can't enter download mode, disconnect the relay IN during flashing (or rewire to a non-strapping pin like `GPIO23` and update `RELAY_GPIO`). RGB status LED via LEDC on `GPIO25/26/27` active-high (same wiring as `sensor-zone`). LED status: **BLUE** boot/connecting → **GREEN** connected + server up → **RED** WiFi disconnected → **MAGENTA** while the pump is ON (overrides the status color, restored when it stops).
- Commands: `cd pump-zone && cp include/secrets.example.h include/secrets.h` (fill creds) → `pio run` / `pio run -t upload` / `pio device monitor` (115200). Then `curl -X POST http://<ip>/api/v1/relay -d '{"state":"on"}'`. **Not yet compiled or hardware-verified** — the first `pio run` pulls the pioarduino platform + IDF 5.3.2 (slow, one-time). No native test env in v1.

## pump-zone-esp01/

```
pump-zone-esp01/
├── platformio.ini        # env:esp01_1m — espressif8266 / arduino, ArduinoJson dep, commented espota block
├── README.md             # rewrite rationale, pin map, API, safety, flashing-jig + power caveats
├── .gitignore
├── include/
│   ├── pump_config.h     # COMMITTED hw contract: RELAY_GPIO=0/ACTIVE_LEVEL, STATUS_LED GPIO2, PORT, PUMP_MAX_RUN_MS
│   ├── secrets.h         # gitignored — WIFI_STA_AP_SSID/PASSWORD, DEVICE_ID, OTA_PASSWORD
│   └── secrets.example.h # committed placeholder template
└── src/
    ├── main.cpp          # setup/loop glue: WiFi-up → start web server + OTA; LED priority
    ├── relay.{cpp,h}     # GPIO0 direct drive + dead-man safety timer (each 'on' re-arms)
    ├── status_led.{cpp,h}# single onboard LED (GPIO2, active-low) non-blocking blink codes
    ├── watchdog.{cpp,h}  # SW/HW watchdog feed + lost-link recovery (force pump OFF + reboot)
    ├── web_server.{cpp,h}# ESP8266WebServer + ArduinoJson, /api/v1/relay GET+POST
    └── wifi.{cpp,h}      # STA join + WiFi.setAutoReconnect(true)
```

- **Role in the topology:** identical to `pump-zone` — an HTTP *server* that joins `MJU-SmartFarm-AP-II` as a STA, listens on `PUMP_HTTP_PORT` (80), and switches the pump relay on command. Uses a **static IP `192.168.0.5`** (`USE_STATIC_IP` in `pump_config.h`) instead of a DHCP reservation — `.5` is in ap-server's reserved `.2`–`.99` range, outside its `.100`–`.109` dynamic pool, so no reservation entry is needed (just don't reserve `.5` elsewhere). **The web-server code is deliberately left unchanged** (its default pump target stays `http://192.168.0.4`); this node is selected at runtime via the dashboard **Settings → Pump Control Settings → Pump URL = `http://192.168.0.5`**, which persists in browser localStorage and overrides the code default (no web-server rebuild). `DEVICE_ID = "pump_zone_01"` is cosmetic here (the hub reaches the pump by IP, mirrors its state under `main-pump`). `pump-zone/` (ESP32/ESP-IDF) is left untouched as the reference/fallback.
- **Why a rewrite, not a port:** `pump-zone` is `framework = espidf`, and **ESP-IDF has no ESP8266 target** — none of its foundation (`esp_http_server`, `driver/ledc`, cJSON, FreeRTOS-task model, pioarduino IDF platform) exists on the ESP8266. So it's rebuilt on **Arduino/ESP8266**: `ESP8266WebServer` (was `esp_http_server`), **ArduinoJson** (was cJSON), `WiFi.setAutoReconnect(true)` (replaces the hand-rolled `esp_timer` reconnect), and classic `setup()`/`loop()` (replaces the `main_task` + queue). The **HTTP contract is deliberately identical** so the two are interchangeable in the field.
- **HTTP API:** same as pump-zone — `POST /api/v1/relay` `{"state":"on"|"off"}` and `GET /api/v1/relay`, replying `{"relay_status":"ON"|"OFF"}` — plus two ESP-01-specific fields: `remaining_ms` (time until the safety cutoff while running) and `safety_off:true` when the last OFF was the dead-man timer rather than a command. No auth (WPA2 is the gate).
- **Safety cutoff (new, on by default):** the pump auto-shuts OFF `PUMP_MAX_RUN_MS` (default **5 min**) after the last `{"state":"on"}`; each `on` re-arms the countdown, so a long run is the hub re-POSTing `on` as a heartbeat. A silent/crashed hub can never exceed one window. `0` disables. This is the ESP-01's local protection — pump-zone had no such feature (it dropped the source's auto-irrigation entirely).
- **GPIO reality (ESP-01/01S):** only GPIO0 + GPIO2 are usable and **both are boot straps that must idle HIGH**; TX/RX carry the serial console — total budget is **one relay + one LED**. Relay (pump) on **GPIO0**, `RELAY_ACTIVE_LEVEL` **default active-high** (most ESP-01S relay boards); GPIO0 is also the flash-mode strap, so `relay_init()` forces the pump OFF first (a brief boot-time click is possible and expected). Status on the onboard LED (**GPIO2, active-low**) via blink codes: **fast blink** connecting → **solid** ready → **slow blip** WiFi lost → **double-blink heartbeat** pump running (overrides).
- **OTA (new):** `ArduinoOTA` enabled (hostname = `DEVICE_ID`, password = `OTA_PASSWORD` from `secrets.h`); it force-stops the pump before flashing. Added because wired reflashing an ESP-01 is painful — no USB/auto-reset, and GPIO0 (the relay pin) must be pulled LOW for download mode, so the first flash needs a USB-serial jig with the board off the relay; OTA handles everything after.
- Commands: `cd pump-zone-esp01 && cp include/secrets.example.h include/secrets.h` (fill creds) → `pio run` / `pio run -t upload` (wired, first time) / `pio device monitor` (115200). Then `curl -X POST http://<ip>/api/v1/relay -d '{"state":"on"}'`. **Not yet compiled or hardware-verified** — first `pio run` pulls the espressif8266 platform + ArduinoJson. **Bench-test relay polarity** before deploying (flip `RELAY_ACTIVE_LEVEL` if your board is active-low), and use a supply with headroom (relay coil + WiFi bursts can brown out a weak 3.3 V rail).
